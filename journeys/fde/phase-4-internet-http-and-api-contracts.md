# Phase 4 — Internet, HTTP, and API contracts



**Goal:** Understand the contract across a network boundary before designing integrations.

**Handbook reading path (S69 [TOC]):** Ch. 1 §§1.1, 1.5, 1.7–1.8, 1.10–1.16 (network paths and failure surfaces); Ch. 2 §§2.1–2.4, 2.9–2.10, 2.16–2.18 (HTTP contracts, caching, timeouts, HTTPS); Ch. 7 §§7.1–7.12 (API design, idempotency, concurrency control, evolution, pagination, rate limits, and API documentation); Ch. 9 §§9.1–9.14 and Ch. 10 §§10.1–10.13 (authentication, authorization, object-level access, tenancy, and tests). Provider-specific claims still come from that provider's current docs.

- **P4.1 — Network request mental model** — **Priority:** important. Depends on: P2.2, P3.4. Client/server, DNS at a conceptual level, connection, TLS purpose, and network failure boundaries. **Proof:** trace a request from client to server and name where failures may occur. Source: F4.
- **P4.2 — HTTP request and response anatomy** — **Priority:** important. Depends on: P4.1. Methods, paths, headers, body, status codes, content types, and caching semantics. **Proof:** inspect several real requests/responses and explain their contracts. Source: F4.
- **P4.3 — Resource design and REST-style APIs** — **Priority:** important. Depends on: P4.2, P3.2, P2.2. Resource identity, methods, representation, validation, pagination, and versioning. Boundary: this contract is the single source of truth that the service unit implements (revisited in P4.7a) and the drift fixtures re-test (re-tested by P4.7b); the status/error taxonomy is owned here, not re-decided per endpoint. **Proof:** design an API contract for the capstone before implementation, including an error model (status mapping, stable machine-readable codes, no internal detail leaked, and no 403/404 distinction that lets a caller enumerate resources). Sources: F4, S39 (§2.5, REC-API-23); RFC 9457 and OpenAPI 3.1 (to verify, see `../../workspace/resources.md`).
- **P4.4 — Authentication and authorization basics** — **Priority:** must-have. Depends on: P4.2–P4.3, P3.7. API keys, bearer tokens, OAuth concepts, scopes, ownership checks, and secret hygiene. Issuing your own sessions/tokens and a role matrix for the capstone API is P4.9 — this unit consumes and verifies credentials, P4.9 issues them. **Owned-system lab:** trace one Eagles authorization path from a route handler through `eagles-wrms-app/src/logic-functions/caller-role.helper.ts`, and state what happens on a null role and on a database throw; compare the observed behavior with AD-30's fail-closed rule. **Proof:** test allowed and denied requests, including one cross-user object-access test written from the requirement rather than from the generated handler; state the difference between authentication and authorization. Sources: F4, F11, S39 (§2.2–2.3, REC-API-11–12).
- **P4.5 — HTTP failure semantics and the client retry decision** — **Priority:** must-have. Depends on: P2.3, P4.2. Timeouts, 4xx/5xx categories, 429, `Retry-After`, and why not every error should be retried. This unit decides, per call, which outcomes are retryable from the client side; budgets, backoff curves, jitter, and retry storms are taught once in P8.3. **Owned-system lab:** classify opran's demo retry control (`website/src/app/demo/DemoClient.tsx`, ADR-010) as user-initiated or automatic, and state which failures it does and does not recover. **Proof:** write a client policy table for retryable and permanent outcomes. **AI-dependency bridge:** classify a recorded fixture set of provider-shaped 400/401/403/404/409/429/5xx responses through the P2.1 client; state which outcomes are retryable from the client and which need a contract or credential fix. Budgets and backoff stay in P8.3. Sources: F4, S25, S66.
- **P4.6 — API data contracts and schema evolution** — **Priority:** must-have. Depends on: P2.2, P4.3. Validation, unknown fields, additive/breaking changes, compatibility, and idempotent client behavior. **Proof:** test old and new payload versions; name, from the requirement, which consumer breaks on a breaking change before writing the compatibility test. Sources: F4, F11.
- **P4.7a — Build and test a small HTTP service/client** — **Priority:** must-have. Depends on: P3.1, P3.2, P3.4–P3.7, P4.1–P4.6. Implement one endpoint, one client, validation, errors, and tests against P4.3's contract. **Proof:** reproducible service and contract tests, built from a written delegation brief with an agent review record (§3) for each agent-written part. Sources: F3, F4, F8, S40.
- **P4.7b — Fault-injection stub provider (the shared harness)** — **Priority:** must-have. Depends on: P4.7a. Build one stub provider with switchable fault modes that Phases 8–17 reuse rather than rebuild: latency, 5xx, 429 with `Retry-After`, timeout-after-commit, duplicate and out-of-order delivery, invalid signature or replay, expired or revoked token, schema drift, outage. **Proof:** the harness, with each fault mode triggerable by a named switch and an executable fixture per mode; before any harness code is written, list the observable symptom each fault mode must produce. **Source boundary:** S37 is a vendor benchmark and supports only the failure it documents — an agent declaring success after 400 errors on invalid test data — not the fault list itself; the fault taxonomy comes from S26 ch. 4 (read: the five inter-process failure modes) and S29 ch. 2 (read: delivery semantics). Sources: F3, F4, F8, S26 ch. 4, S29 ch. 2, S37, S40.
- **P4.7 — split into P4.7a (service/client) and P4.7b (fault harness).** Tombstone: dependents re-pointed; the stub fault modes now live in P4.7b.
- **P4.8a — Third-party API onboarding: provider contract sheet and drift tests** — **Priority:** must-have. Depends on: P4.4–P4.6, P4.7a–P4.7b. Document what the provider guarantees instead of assuming it: authentication model, scopes and permissions, quotas and rate limits, pagination, idempotency support, webhook delivery, ordering, and replay behavior, schema and versioning policy, and sandbox-versus-production differences. Scope the sheet to the endpoints the capstone actually calls; the first pass covers only those, and other provider claims stay questions. **Proof:** a contract sheet for one real or sandbox API with every claim tagged documented (canonical URL and section), observed (fixture or test), or unknown; contract tests plus a drift test against the P4.7b harness that fails on a changed fixture; agent-written client code checked against the sheet, with each mismatch recorded as a finding. Sources: F4, F11, S19 ch. 5 [TOC], S27 ch. 5 [TOC], S37, S39 (§2.3, REC-API-11, REC-API-15–16); RFC 9700 and OpenAPI 3.1 (to verify, see `../../workspace/resources.md`).
- **P4.8b — Credential lifecycle and provider failure matrix** — **Priority:** must-have. Depends on: P4.8a. Token acquisition, expiry, refresh, revocation, and secret rotation where the provider's documented contract calls for them. **Proof:** a credential-lifecycle test, with the provider's documented expiry and revocation behavior stated in one line before the test is written, including concurrent requests at token expiry where the provider issues expiring tokens; a failure matrix for provider-side faults using the section 3 failure-matrix template with a provider-specific delta (no new format). Sources: F4, F11, S19 ch. 5 [TOC], S27 ch. 5 [TOC], S39 (§2.3, REC-API-11, REC-API-15–16); RFC 9700 (to verify, see `../../workspace/resources.md`).
- **P4.8 — split into P4.8a (contract sheet + drift tests) and P4.8b (credential lifecycle + failure matrix).** Tombstone: dependents (P8.4, P8.7) re-pointed to P4.8a.
- **P4.9 — Issue and rotate your own auth: sessions, tokens, and role matrix** — **Priority:** must-have. Depends on: P4.4, P4.8a–P4.8b, P4.7a. Boundary: P4.4 consumes and verifies credentials; this unit issues and revokes them for the capstone API — issuance, expiry, rotation, revocation, and a role matrix for allowed/denied actions. The provider-side lifecycle was P4.8b; this unit owns your service's. The lesson teaches the signing, expiry, and rotation mechanics before the role matrix is built. **Proof:** an issued credential expires on schedule, is rejected after revocation, and the role matrix denies one cross-role action (P4.4's cross-user test pattern reused against issuance). Sources: F4, F11, S39 (§2.2–2.3, REC-API-11–12).
