# Phase 12 — Context engineering, retrieval, RAG, and memory



**Goal:** Provide the model with relevant, permissioned information and measure whether retrieval actually helps.

**Lesson sequence (S48):** Start with context as a limited budget; add just-in-time retrieval and document lifecycle controls; compare lexical, vector, hybrid, and reranked retrieval; finish with grounded citations, abstention, and state/memory boundaries. Do not start with a vector database or an agent framework.

**Handbook reading path (S69 [TOC]):** Ch. 33 §§33.1–33.8, 33.12–33.14 (embeddings, keyword/semantic/hybrid search, vector storage choices, ingestion, RAG, advanced retrieval, evaluation, data model, feature-level cost/latency, UX); Ch. 13 §13.17 and Ch. 17 §17.8 (PostgreSQL full-text/trigram search and when full-text search may suffice). Ch. 34 is optional only if the chosen workflow has Arabic/multilingual requirements; Ch. 18 §18.23 is considered only after cache value and invalidation risks are evaluated.

- **P12.1 — Context engineering and information budgets** — **Priority:** important. Depends on: P11.1–P11.2. Select useful context, keep it current, and avoid flooding the model with irrelevant material. Assembly decisions include provider-documented prompt structure (S49): section or XML tags that separate instructions from data and examples, examples chosen as few steering shots rather than exhaustive rules, and quote-grounding inside long document input. **Proof:** compare two context assembly strategies using fixed examples. Sources: S5, F12, S49.
- **P12.2 — Data ingestion and document lifecycle** — **Priority:** important. Depends on: P5.1–P5.6, P12.1. Coupled with: P15.4. Sources, parsing, metadata, versioning, deletion, and permission inheritance. Permission inheritance, retention, and deletion are designed at ingestion time, not retrofitted: build the hooks now so the later system-wide review in P15.4 verifies them instead of adding them. **Proof:** ingestion pipeline with provenance, a recorded re-index/delete test, and a note listing which permission and retention decisions P15.4 must review. Sources: S5, F12 (context selection); the ingestion/access-control lifecycle itself is NO-EVIDENCE — see `../../workspace/resources.md` coverage gaps.
- **P12.3 — Chunking, embeddings, lexical search, and vector search** — **Priority:** important. Depends on: P12.2, P11.2. Understand the pipeline and what each retrieval method contributes without prematurely choosing a vector database. Engineering scope only (rule 9): treat chunking/embedding settings as API parameters and measure their effect; no model training or embedding math. **Proof:** inspect results for a small controlled corpus. Sources: F12, S5.
- **P12.4 — Retrieval pipeline: filters, hybrid search, reranking** — **Priority:** important. Depends on: P12.3, P4.4, P4.6, P9.3. Improve recall/relevance while preserving tenant and access filters (the authorization tests come from P4.4 — the filter must not merely prefer the user's tenant but deny others). One considered alternative at vocabulary depth, no lab (S53): GraphRAG — extracted entity/relationship graphs with hierarchical community summaries target multi-hop "connect the dots" questions and holistic corpus summarization where similarity-based chunk search loses the links, priced by LLM-heavy indexing runs; it is a documented option for the capstone retrieval decision, not a required exercise. **Proof:** retrieval results with measured top-k quality on a labelled set. Sources: F12, S5, S53.
- **P12.5 — RAG grounding, citations, abstention, and failure taxonomy** — Implementation unit (multi-session). **Priority:** important. Depends on: P12.1–P12.4, P11.3. Distinguish retrieval failure, missing source coverage, synthesis error, and unsupported answer. Practice shape from the designated roadmap (S48): the corpus slice doubles as a small grounded-question demo — hybrid retrieval with rerank feeding cited answers that abstain when evidence is missing, exposed through one read-only retrieval tool — i.e., a slice of this unit's proof, not a separate build. **Proof:** label a test set by failure type and make the system abstain appropriately. Sources: S31 (FP1 missing content, FP2 missed top-rank, FP3 consolidation exclusion, FP4 extraction failure under noise/contradiction, FP5 wrong format, FP6 specificity, FP7 incompleteness), S48. Residual gap: chunking/embedding/reranking tuning depth (their §6 future work) — label it as such.
- **P12.6 — Evaluate retrieval separately from generation** — **Priority:** important. Depends on: P12.4–P12.5. Measure whether the right evidence was retrieved before judging the final answer. The grader-side statistical caveat (how much run-to-run noise a small labelled set may hide) is stated once in P14.3 — this unit applies that caveat, it does not depend on Phase 14's units. A documented metric-library option (S54): Ragas publishes faithfulness, context precision, context recall, and response-relevancy metrics that can replace hand-rolled retrieval checks — adopting one is an implementation choice, and its scores still require this unit's n-and-range discipline. Coupled with: P14.3. **Proof:** report retrieval and answer-quality results separately, with n and observed range. Sources: S15, S54; S22 (deprecated — see the S22 note in §7); the P14.3 statistics caveat applies.
- **P12.7 — Conversation state, durable memory, compaction, and freshness** — **Priority:** useful. Depends on: P6.5, P12.1–P12.6. Separate session state, durable business facts, retrieved knowledge, and generated summaries. **Proof:** define state ownership, retention, expiry, and update rules. Sources: S5, S8, S13.
