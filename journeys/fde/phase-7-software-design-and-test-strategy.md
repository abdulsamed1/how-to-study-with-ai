# Phase 7 — Software architecture and design strategy

**Goal:** Design systems around real business responsibilities and quality constraints. Keep components understandable, changes verifiable, and architecture decisions explicit before implementation.

**Handbook reading path (S69 [TOC]):** Ch. 21–23 and 28 as mapped below. Use *Fundamentals of Software Architecture*, *Software Architecture: The Hard Parts*, and *Building Microservices* for architecture fundamentals; current framework behavior remains subject to current official docs.

- **P7.1 — Boundaries, responsibilities, and dependency direction** — **Priority:** important. Depends on: P2.5, P3.1–P3.2, P3.4–P3.7, P4.7a. Separate transport, application use cases, domain rules, and persistence where useful. Introduce ports/adapters and dependency inversion as boundary tools, not mandatory folder templates. **Proof:** draw a module diagram, justify boundaries, and add an automated check that fails on a deliberate dependency-direction violation. Sources: S20 ch. 2–3 and 20 [TOC]; S26 ch. 2–3 (read).
- **P7.2 — Unit, integration, contract, and end-to-end tests** — **Priority:** must-have. Depends on: P2.2, P4.7a, P5.6. Choose the test level that proves a claim; avoid testing implementation details unnecessarily. **Proof:** test one important invariant at multiple appropriate layers, with one requirement-first test shown to fail under a seeded defect. Sources: F8, S20, S40, S41.
- **P7.3 — Test doubles and dependency boundaries** — **Priority:** must-have. Depends on: P7.1–P7.2. Know when a fake, stub, or real dependency improves confidence and when it hides a defect. **Proof:** replace one brittle test without losing meaningful integration coverage; identify a defect a mock-coupled suite would miss. Sources: F8, S41.
- **P7.4 — Refactoring under tests and code review** — **Priority:** must-have. Depends on: P7.1–P7.3, P2.1–P2.2. Change structure without silently changing behavior. **Proof:** a reviewed refactor with regression tests, explanatory diff, independent verification, and an agent review record when an AI coding tool produced the change. The learner explains and modifies the result unaided. Sources: S34, S37, S40, S41; S26 ch. 7–9 [TOC].
- **P7.5a — Architecture characteristics, quality scenarios, styles, and decomposition** — **Priority:** important. Depends on: P7.1–P7.4. Identify relevant quality attributes, turn them into measurable scenarios, and compare layered, modular-monolith, service-based, event-driven, and microservice styles against the simplest adequate option. Introduce cohesion, coupling, deployability, operational coupling, and data ownership; deeper domain and decomposition work is P7.9–P7.10. **Proof:** quality-attribute table with measurable targets and methods, plus comparison of at least two architecture styles with explicit trade-offs. Sources: S20 ch. 4–6, 11, 19 (read); S26 ch. 2–3; S38 ch. 2–5 and 7 [TOC]; S19 ch. 1–2.
- **P7.5b — Architecture diagrams and architectural decision records** — Implementation unit (multi-session). **Priority:** important. Depends on: P7.5a. Communicate context, containers/components, dependencies, and runtime interactions. Record context, requirements, alternatives, constraints, rationale, consequences, risks, and revisit conditions before implementation. **Proof:** ADR comparing at least three plausible options, including the simplest adequate option and modular-monolith versus separately deployed alternatives, plus appropriately scoped architecture diagrams. Sources: S20 ch. 19, 21, 23; S38 ch. 1 and 15 [TOC]; S42.
- **P7.5c — Fitness functions and architecture risk analysis** — Implementation unit (multi-session). **Priority:** important. Depends on: P7.5a–P7.5b. Make selected architectural constraints observable and test risky assumptions before commitment. **Proof:** one validated fitness check and a risk assessment listing assumptions, impact, and the cheapest verification method. Sources: S20 ch. 6 and 22; S41.
- **P7.6 — Evolutionary architecture and build-vs-buy** — **Priority:** important. Depends on: P7.5b–P7.5c. Identify expensive-to-reverse decisions, revisit triggers, ownership cost, lock-in, and differentiation. **Proof:** extend the ADR with one evolutionary decision and one build-vs-buy comparison whose cost assumptions are explicit. Sources: S26 ch. 16 (read); S38 ch. 15 [TOC]; S33.
- **P7.7 — Next.js server/client boundary and data flow** — Implementation unit (multi-session). **Priority:** important. Depends on: P2.3, P3.1, P4.3, P4.7a, P7.1. Conditional code-reading scope for the named existing system, not a Next.js track. Map server-rendered, cached, client-fetched, and streamed data; cancellation and race behavior. **Proof:** one route data-flow map with an evidence-backed failure mode and verification check. Sources: S47 and the named existing-system files/ADRs.
- **P7.8 — Twenty host and Apps extension model** — Implementation unit (multi-session). **Priority:** important. Depends on: P3.4, P3.7, P4.4, P7.1, P7.5b. Conditional platform literacy, not a NestJS track. Separate host responsibilities from application-owned logic and verify claims against code. **Proof:** host-versus-app boundary map and one verified logic-function path. Sources: S45, S46, and named existing-system files.
- **P7.9 — Domain modeling, bounded contexts, and domain events** — Implementation unit (multi-session). **Priority:** important. Depends on: P6.6, P7.1, P7.5a. Learn domain-driven design as a way to model business language and consistency boundaries: ubiquitous language, entities/value objects, aggregates, bounded contexts, context maps, domain events, and event storming. Distinguish an aggregate consistency boundary from a deployable service boundary. Use the booking/PMS workflow or another capstone workflow; do not create microservices as an automatic consequence of drawing bounded contexts. **Proof:** domain glossary, context map, one aggregate with explicit invariants, and a domain-event model reviewed against real workflow exceptions. Sources: S26 ch. 2; S20 ch. 18 [TOC]; S38 ch. 5 and 9 [TOC].
- **P7.10 — Component decomposition, data ownership, and service granularity** — Implementation unit (multi-session). **Priority:** important. Depends on: P7.5b–P7.6, P7.9. Move from domain model to deployable architecture: static and dynamic coupling, cohesion, architecture quantum, component decomposition, operational data ownership, distributed data access, service granularity, and the cost of integration versus disintegration. Compare in-process modular boundaries with separately deployed services and explain when a shared database becomes an ownership constraint. **Proof:** component/data-ownership map and decomposition ADR that names one candidate boundary, its coupling, data owner, operational consequences, and conditions that would justify a separate deployment. Sources: S38 ch. 2, 4, 6–7, 9, 13 (selected sections read); S26 ch. 2–3 and 5 (selected sections read); S20 ch. 8–9 and 11 (selected sections read).
