# Phase 5 — Data engineering and database systems

**Goal:** Model business facts correctly, choose storage structures that fit the workload, and understand the database mechanisms that affect durability, query behavior, and growth.

**Handbook reading path (S69 [TOC]):** Ch. 12–16 as mapped below. These are navigation pointers only until the exact passages are read and recorded. Use PostgreSQL 18 documentation for PostgreSQL-specific behavior; do not generalize it to every database engine.

- **P5.1 — Relational modeling and data invariants** — **Priority:** important. Depends on: P2.3, P4.3. Entities, relationships, keys, cardinality, nullability, and invariants. **Proof:** schema sketch for users, requests, events, and processing state. Source: F6.
- **P5.2 — SQL reads/writes, joins, and aggregation** — **Priority:** must-have. Depends on: P5.1. CRUD, filtering, NULL semantics, joins, grouping, ordering, and transaction boundaries. Add CTEs, window functions, and RETURNING/UPSERT when a business question requires them. **Proof:** answer representative business questions with SQL rather than application loops, including one ranked/top-per-group query and one safe write whose result is checked. Sources: F6; S69 ch. 13 §§13.1–13.10 [TOC].
- **P5.3 — Constraints and integrity** — **Priority:** must-have. Depends on: P5.1–P5.2. Primary/foreign keys, uniqueness, check constraints, and why application checks alone can race. **Proof:** encode key invariants in the database. Source: F6.
- **P5.4 — Indexes and query plans** — **Priority:** important. Depends on: P5.2–P5.3. Query patterns, selectivity, composite/partial indexes, EXPLAIN versus measured execution, and index write/storage cost. Include N+1 and OFFSET-versus-keyset pagination when the measured access pattern makes them relevant. **Proof:** capture the same query's plan and measured latency before/after one justified index or query-shape change, and state the trade-off. Sources: F6; S76; S69 ch. 14 [TOC].
- **P5.5 — Schema migrations and safe change** — **Priority:** must-have. Depends on: P5.1–P5.4, P2.1. Versioned changes, backfills, deploy order, compatibility, and rollback limits. **Proof:** perform an additive migration and one expand → backfill → contract change while old and new application versions both pass tests against the intermediate schema. Source: F6.
- **P5.6 — Database access from the application** — **Priority:** must-have. Depends on: P3.4, P4.7a, P5.1–P5.5. Parameterized queries or a query builder, connection pooling, mapping, and validation. **Proof:** persist and retrieve capstone records with tests; explain what the connection pool bounds. Sources: F3, F6.
- **P5.7 — Backup, restore, and data lifecycle basics** — **Priority:** important. Depends on: P5.5–P5.6. What backups protect, retention/deletion, and restore verification. This unit owns data-level evidence; service-level recovery drills remain in P9.7. **Proof:** document and test a local recovery procedure. Sources: S25, F10, F6.
- **P5.8 — Data models and storage choice** — **Priority:** important. Depends on: P5.1–P5.2. Compare relational, document, key-value, graph, and analytical models by access pattern, relationship shape, consistency needs, query needs, and operational cost. Distinguish OLTP from analytical workloads. Do not implement multiple database products just to complete the comparison. **Proof:** a workload-to-data-model decision record that includes the simplest adequate option, query examples, and the consequences of changing the choice. Sources: S19 ch. 3 (read: data models and query languages); S20 ch. 8 (read: logical versus physical architecture); S28 ch. 3 [TOC].
- **P5.9 — Storage engines, indexes, WAL, and durability** — **Priority:** important. Depends on: P5.2, P5.4, P5.6. Understand pages, B-trees, log-structured storage/LSM trees, sorted-string tables, memtables, compaction, Bloom filters, write amplification, and the role of a write-ahead log in durability and recovery. Treat these as engine concepts, not a requirement to build a storage engine. **Proof:** compare a read-heavy and write-heavy workload, explain the likely storage/index trade-offs, and trace how PostgreSQL WAL supports recovery using the documented behavior. Sources: S19 ch. 4 (read: storage and retrieval); S76, PostgreSQL 18 docs, ch. 28 §§28.3–28.6.
- **P5.10 — Table partitioning and large-table lifecycle** — **Priority:** useful. Depends on: P5.4–P5.5, P5.8. Distinguish partitioning one database table from sharding data across independent database nodes. Understand range/list/hash partitioning, partition pruning, retention operations, partition maintenance, and the operational cost of too many partitions. **Proof:** design a partition key for a measured or explicitly stated workload, test partition pruning, and document the maintenance and migration plan. Sources: S76, PostgreSQL 18 docs, §5.12; S19 ch. 7 (read: sharding and when to avoid it).
