# Phase 8 — Integration and distributed-systems foundations



**Goal:** Reason about boundaries where networks, retries, queues, and independent state make success ambiguous. Practise each unit against the P4.7b stub provider, and design each unit's tests from the P8.1 failure timeline and the P4.8a contract sheet before reading any agent-written implementation.

**Handbook reading path (S69 [TOC]):** Ch. 19 §§19.1–19.13, 19.15–19.21 (delivery semantics, acknowledgements, retries, idempotent consumers, ordering, poison messages, progress, outbox, backpressure, queue monitoring); Ch. 20 §§20.1, 20.3–20.11, 20.19–20.21 (integration boundaries, timeout/retry safety, circuit breakers, bulkheads/fallbacks, rate limits, partial failures, webhooks, secrets in telemetry, testing); Ch. 31 §§31.1–31.2, 31.8–31.11, 31.13, 31.19–31.20 (partial failure, locks, clocks, exactly-once limits, sagas, resilience, cross-service traces, idempotent APIs).

- **P8.1 — Partial failure and ambiguous outcomes** — **Priority:** important. Depends on: P4.5, P6.1–P6.5. A timeout does not tell the caller whether the remote side effect occurred. **Proof:** failure timeline for a request that times out after the remote write, expressed as rows of the section 3 failure-matrix template plus the timeline that provoked each row (reuse; the delta is the ambiguous-write column). Sources: S26 ch. 4 (read: the five inter-process failure modes — crash, omission, timing, response, arbitrary), S29 ch. 2 (read: idempotency and delivery semantics), S64 (read: a connection error leaves the client unable to tell whether the request succeeded, so a retry needs an idempotency key), S65 (read: a lost response followed by a retry); S27 ch. 6–7 [TOC].
- **P8.2 — Idempotency and deduplication** — **Priority:** must-have. Depends on: P6.5, P8.1. Stable operation keys, duplicate semantics, retention, and the role of database uniqueness. **Owned-system lab:** take Eagles' lead-status transition idempotency (`eagles-wrms-app/src/logic-functions/transition-lead-status.logic-function.ts`, the early return when the status is unchanged) and the Meta `leadgen_id` duplicate path, then name the operation key and the retention limit each one relies on. **Proof:** repeat a request, sequentially and concurrently, and show it cannot create a second business effect. Sources: S29 ch. 2 (read: what idempotency is and why it makes failure handling easier); S64 (read: idempotency keys on mutating endpoints, the saved response returned on retry including `500` errors, key pruning, and parameter matching), S65 (read: request- versus entity-level keys, expiring leases, response recording, and master-only idempotency reads); S19 ch. 8 and 13 [TOC], S27 ch. 5 [TOC].
- **P8.3 — Retry budgets, backoff, jitter, and timeouts** — **Priority:** must-have. Depends on: P4.5, P8.1–P8.2. Scope boundary: P4.5 decided which single outcomes are retryable from the client; this unit owns the budget mechanics around them — transient/permanent classification at the workload level, deadlines, retry storms, and synchronized retries. Enforcing a quota on your own endpoints is overload control (P10.5), not this unit. **Proof:** bounded retry policy with a testable budget that honors a provider-supplied retry delay. **AI-dependency bridge:** run the P4.7b harness's 429-with-`Retry-After` and transient-5xx modes under a fixed budget and show that attempt count and elapsed time stay bounded. Sources: S25, F10; S29 ch. 16 (read: retry amplification, exponential backoff, jitter, circuit breaker); S10 (read: recovery herd caused by missing randomized exponential backoff — an internal control-plane failure, not a provider-specific 429/5xx case), S66 (read: timeouts, capped exponential backoff, jitter, retry amplification across layered services, retry at a single point); S19 ch. 9 [TOC], S27 ch. 27 [TOC].
- **P8.4 — Webhook receiver and sender contracts** — **Priority:** must-have. Depends on: P4.2–P4.6, P4.8a, P6.5, P8.1–P8.3. Verify signatures, validate events, acknowledge deliberately, persist receipt, enqueue durable work, and process idempotently. **Owned-system lab:** audit Eagles' Meta webhook receiver (`eagles-wrms-app/src/logic-functions/meta-lead-ingestion.logic-function.ts`) against this unit's checklist: raw-body HMAC, timing-safe compare, size limit, replay/dedupe, and failure response; record each as present, partial, or absent. **Proof:** locally tested webhook flow with invalid signature, replay attempt, duplicate, out-of-order, transient failure, and crash-window tests, with the signature checked against the raw request bytes where the provider requires it (confirm in current provider documentation). **AI-dependency bridge:** treat a provider webhook as model-adjacent untrusted input; the acknowledgement decision is made before any parsing that can fail slowly. Sources: S67 (read: webhook secret, HTTPS, the 10-second response bound, event and action checks, redelivery, `X-GitHub-Delivery` replay guard, HMAC-SHA256 in `X-Hub-Signature-256`, timing-safe compare, payload left unmodified), S68 (read: raw-body requirement for `Stripe-Signature`, timestamp tolerance against replay, duplicate event IDs, no ordering guarantee, asynchronous processing, 2xx before complex work); F11 for general API risks; S26 ch. 4 (read: rolling out an interface change across separately deployed services, error semantics).
- **P8.5 — Queues, workers, and at-least-once delivery** — **Priority:** must-have. Depends on: P3.5–P3.6, P5.6, P8.2–P8.3. Consumer retry, delayed work, dead-letter strategy, per-key ordering, and idempotent consumers. **Proof:** worker that can restart without duplicating business effects. Sources: S19, S26.
- **P8.6 — Dual writes, outbox, saga, compensation** — **Priority:** must-have. Depends on: P6.4, P8.1–P8.5. Understand why independent writes can diverge and distinguish atomic database updates from cross-system workflows. **Proof:** implement a transactional outbox in Python and PostgreSQL, reuse the P4.7b fault-injection harness for the kill point instead of building new crash tooling, crash the worker between database commit and publish, restart it, and show each event is published at least once and consumers deduplicate it (P8.2). Sources: S19 ch. 8 (read: a distributed transaction can commit on some nodes and fail on others, and a committed transaction cannot be retracted), ch. 13 [TOC], S26, S27 ch. 6–13 [TOC range], S38 ch. 11–12 [TOC]; transactional-outbox lead (unopened).
- **P8.7 — Synchronization and reconciliation loops** — **Priority:** must-have. Depends on: P4.8a, P6.5, P8.2–P8.6. Full/delta sync, watermarks, cursors, drift detection, source of truth, replay, and repair. **Proof:** reconciliation report that classifies missing, duplicate, stale, and conflicting records, plus a replay test that repairs them without creating duplicates. Sources: S19 ch. 12 (read: consumer offsets, per-partition total order, replay from the log), ch. 13 [TOC], S26, S27 ch. 10–11 [TOC].
