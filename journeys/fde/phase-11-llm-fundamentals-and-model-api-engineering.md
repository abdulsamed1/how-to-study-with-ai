# Phase 11 — LLM fundamentals and model API engineering



**Goal:** Treat a model as a probabilistic component behind an explicit software contract.

**Lesson sequence (S48):** Teach the model contract first; then request shape and structured output; then prompt/context versioning and prompt caching; finish by deciding where an LLM belongs and what contains its failures. Use one small provider-backed example, and require a typed result plus a visible failure before moving on.

**Handbook reading path (S69 [TOC]):** Ch. 32 §§32.1–32.2, 32.4–32.5, 32.7–32.10, 32.13–32.14, 32.18 (model guarantees at backend depth, request shape, streaming, structured output, prompt design, reliability, cost/latency, tracing, evaluation, quota control). Skip §32.3's NestJS implementation example; implement the adapter in Python and recheck every live provider detail against its current official docs.

- **P11.1 — What a language model does and does not guarantee** — **Priority:** important. Depends on: P10.2, P4.6. Generation, nondeterminism, context limits, stale knowledge, and confident errors at an engineering level; no unnecessary ML math. **Proof:** list use-case-specific failure modes and what cannot be guaranteed. Sources: S3, S11.
- **P11.2 — Request anatomy, tokens, context window, and response metadata** — **Priority:** must-have. Depends on: P11.1, P2.2, P2.4 (adapter contract only; the adapter is re-implemented, not shared, in this phase's runtime). Messages, instructions, output limits, finish reasons, sampling settings (temperature, top-p), and provider-specific request/response contracts. Failure modes to teach explicitly: context-budget overrun, finish reasons that signal incomplete output, and metadata misuse (token counts versus billed tokens; mixing conversations). Treat streaming as an explicit product/API choice, not a default: if selected, define partial-output, cancellation, timeout, and client-disconnect semantics before implementation. **Proof:** build a minimal model call in Python using the P2.4 adapter pattern (async HTTP client, typed requests/responses, and explicit error handling), log safe request metadata, and state what the finish reason and token counts mean for one hand-written request. Add a streaming response only if the workflow requires it, with a tested disconnect/cancellation path. Sources: S4, S21; S69 ch. 32 §§32.2, 32.4 [TOC].
- **P11.3 — Structured outputs and runtime validation** — **Priority:** important. Depends on: P2.2, P11.2. JSON/schema-constrained output where supported, parse/validation failure, and bounded repair. Additions: what a schema-constrained call does NOT guarantee (empty strings, cross-field consistency, prompt-injected content that still parses); schema evolution across prompt versions (a changed schema must invalidate recorded behavior, per the P11.5 versioning rule); and the multi-turn contract (earlier invalid outputs re-enter the context and require explicit exclusion). **Proof:** invalid model output cannot reach the domain layer unvalidated. Builds on P2.2; do not re-teach validation. Sources: S4, S21.
- **P11.4 — Model errors, rate limits, latency, cost, caching, and budgets** — **Priority:** important. Depends on: P8.3, P9.3, P11.2. Provider failures, concurrency caps, request budgets, token accounting, and timeout behavior. Provider-documented latency and cost levers (S51, S52): fewer requests, parallel independent calls, and above all fewer output tokens (a ~50% output-token cut approximates a ~50% latency cut, while input-token trimming buys only a few percent); model routing — a smaller model for well-scoped, low-risk steps; provider-side prompt caching — stable prompt prefixes reused across requests via checkpointed prefix ordering, priced per token and invalidated when the prefix changes, with usage fields separating cache reads from writes (S50); application-level semantic caching is a vocabulary-level option whose hit-rate and staleness must be measured before adoption (S48). **Proof:** cost/latency/error budget and tested fallback behavior, plus one logged request pair showing the cache-usage fields on a repeated stable prefix and the miss that follows a prefix change. Sources: S4, S21, S48, S50, S51, S52.
- **P11.5 — Prompt/context versioning and model changes** — **Priority:** important. Depends on: P11.2–P11.4. Treat prompts, schemas, retrieval settings, sampling parameters, and model identifiers as versioned inputs to behavior: every artifact that can silently change model behavior is stored, versioned, and recorded with what a change invalidates. The failure this addresses: an unversioned prompt or model swap ships with no way to say what behavior changed. **Proof:** versioned configuration for all four artifact types plus a change record stating what each change invalidates (evaluation cases, fixtures, regression expectations); the evaluation rerun after such a change is exercised in P14.4, revisited in that unit's regression gate — do not re-teach it here. Sources: S4, S15; S22 (deprecated — see the S22 note in §7).
- **P11.6 — Decide where an LLM belongs in the architecture** — **Priority:** important. Depends on: P10.2, P10.4c, P11.1–P11.5. Role split: this is the model-informed revisit of P10.2's provisional comparison — it answers where the LLM belongs and what contains its failures; the pattern mechanics are revisited in P13.1. Keep deterministic invariants outside the model when possible; define fallback and human-review boundaries. One Depth-1 decision line, owner-approved as removable scope: state when fine-tuning or self-hosting weights would be justified — the designated roadmap's heuristic is that it is a cost/risk step taken only after prompting, retrieval, and model choice have demonstrably stopped helping, and it shifts evaluation, security, and serving ownership onto the system (S48; no lab content, no training tooling). **Proof:** updated ADR (extending the P10.2 comparison) with failure containment and reasons not to use an LLM in selected steps, including whether the model call runs in-process through a Python SDK or as a separate service behind a stable contract, and why. Sources: S3, S12, S48.
