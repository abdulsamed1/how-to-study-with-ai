# Phase 13 — Workflows, tools, agents, and MCP



**Execution-order note:** Phase 13 follows the Phase 14 evaluation baseline by design. Start agent work with the Docs Q&A golden set and regression gate already in place, then add agent-specific cases to that same suite.

**Goal:** Increase autonomy only when the workflow needs it and controls are adequate.

**Lesson sequence (S48):** Begin with fixed workflows and compare them with an agent; define tool schemas and permissions; add a bounded loop with step, time, and cost limits; then add checkpoints, human approval, and MCP integration. Treat multi-agent, voice, and browser surfaces as optional comparisons that require evaluation evidence.

**Handbook reading path (S69 [TOC]):** Ch. 32 §§32.6, 32.8, 32.11, 32.13, 32.17 (tool calls, reliability, prompt-injection/data protection overview, LLM observability, agents/MCP); Ch. 19 §§19.3–19.10, 19.20–19.21 (worker bounds, delivery, retries, idempotent consumers, backpressure, monitoring); Ch. 36 §36.29 (safe use of coding assistants). Keep the workflow/single-agent baseline first; framework- or provider-specific implementation is chosen only after the contract and evaluation are clear.

- **P13.1 — Workflow patterns before agents** — **Priority:** important. Depends on: P7.1, P10.2, P11.6. Role split: where P10.2 decided whether AI is justified and P11.6 where the model call sits, this unit supplies the pattern mechanics — chaining, routing, parallelization, orchestrator/worker, and evaluator/optimizer. **Proof:** map a task to a workflow pattern and explain why. Sources: S3, S12, S23 (current official SDK documentation covering the same workflow patterns; verify its examples at teach time).
- **P13.2 — Tool contracts and safe tool design** — **Priority:** important. Depends on: P4.6, P6.6, P8.2, P11.3. Explicit arguments, schema, permissions, side effects, clear errors, and idempotency (deduplication mechanics from P8.2 applied to tool invocations). When a tool must run model-written code, that code executes inside an isolated sandboxed runtime — no standing credentials, resource limits, and timeouts; never in-process (S14 states this boundary as the article's own caveat: sandboxing, resource limits, and monitoring are required for agent-generated code; S56 documents a concrete managed-sandbox option). The same article's code-API framing of tools is context-economics background, not a license to widen the boundary. **Proof:** implement a read-only tool with adversarial input tests. Sources: S7, S14, S21, S56.
- **P13.3 — Agent loop, stop conditions, and budgets** — **Priority:** important. Depends on: P13.1–P13.2, P8.2–P8.5, P11.4. Define state, action, observation, explicit terminal outcomes, maximum steps, a wall-clock deadline, token/cost budgets, and failure recovery. The harness must distinguish completed, failed, and budget-stopped runs; a capped run returns a partial result and stop reason rather than hanging or claiming success. Practice shape from the designated roadmap (S48): build a small research-agent slice that records each step and produces a cited report from URLs actually opened. Use a read-only research tool; execute model-written code only in the isolated sandbox from P13.2 when the task requires computation. A planner-worker decomposition is optional and must beat the single-agent/workflow baseline on the Phase 14 suite enough to justify its added cost, latency, and failure surface. **Proof:** a bounded agent cannot run forever or repeat a harmful side effect; the low-step-cap test stops with a partial report and explicit reason, and one normal run records steps, token/cost usage where available, tool results, and source citations. Sources: S3, S13, S21, S48.
- **P13.4 — State, checkpoints, and long-running workflows** — **Priority:** important. Depends on: P6.1–P6.5, P8.5–P8.7, P13.3. Resume work safely after interruptions and preserve an auditable progress record. **Proof:** kill and resume a job without losing correctness. Sources: S13, S19.
- **P13.5 — MCP and external tool integration** — **Priority:** important. Depends on: P4.4, P13.2–P13.4. Coupled with: P15.2, P15.3 (gate G7 closes the loop: the prompt-injection and least-privilege review verifies the boundary this unit documents). Understand the protocol boundary, server trust, authorization, and the difference between interoperability and safety. Interoperability is not safety: the authorization and consent rules are implemented here and re-audited in Phase 15, so nothing in this unit needs Phase 15's text as a prerequisite. Agent-to-agent protocols at vocabulary depth (S55): A2A standardizes discovery, task delegation, and result exchange between opaque agents built on different frameworks, and the site itself frames it as complementary — MCP connects an agent to its tools and data; A2A lets independent agents delegate to each other without sharing internal state — so cross-agent delegation is a separate interop boundary with its own authorization questions, not a way to bypass this unit's tool consent rules. **Proof:** connect one low-risk tool and document its trust/permission boundary. Sources: S6 (pin the spec date in the lesson record — the current version and date are in `../../workspace/resources.md` S6; authorization is OAuth 2.1 with RFC9728 discovery and RFC8707 audience binding; tool descriptions are untrusted; explicit user consent before invocation; verify at teach time), S14 (read in full 2026-10-21 — see the S14 row), S55.
- **P13.6 — Multi-agent systems and delegation economics** — **Priority:** useful. Depends on: P13.1–P13.5. Coupled with: P14.1–P14.3 (gate G8 closes the loop: any multi-agent choice must be validated against the Phase 14 evaluation set before adoption; without it the default is a single-agent/workflow baseline). Learn when parallel agents help and when coordination, latency, cost, and failure risk outweigh benefits; this unit can be completed as a trade-off comparison with stated hypotheses. **Proof:** compare a single-agent/workflow baseline to a justified multi-agent design; default is not to use multiple agents. Source: S8.
- **P13.7 — Voice and browser agent interfaces** — **Priority:** useful. Depends on: P11.4, P13.2, P13.3, P13.5. Same agent building blocks, different transport (roadmap-scope topics, added per the designation; S57, S58): voice changes the interaction loop — three documented architectures (full-duplex live model with a delegated backend, speech-to-speech session, and an inspectable chained STT→agent→TTS pipeline), with timing, interruption, and session-reliability evaluated as separate properties from task success; browser changes the action surface — a maintained browser-agent tool class exists (local library or hosted browser) whose DOM drift and anti-bot CAPTCHA flows are tool failure modes, and any web page the browser opens is model-adjacent untrusted content governed by the same trust rules as tool results. Design and evaluate the workflow core identically for both; the audio transport and page rendering add latency budgets and modality-specific failure handling, nothing else changes structurally. These modality interfaces are capstone-optional: a voice or browser surface is justified only when the selected workflow genuinely needs it, and the text API remains the default. **Proof:** a written modality comparison for one capstone-relevant workflow — latency budget, cost-per-interaction drivers, modality-specific failure modes, and a justified go/no-go decision. Sources: S48, S57, S58.
