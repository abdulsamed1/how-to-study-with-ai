# Phase 2 — AI-engineering implementation bridge



**Goal:** Work reproducibly in a repository, diagnose behavior instead of guessing, and bridge existing C++/OOP/DSA experience into the runtimes and data contracts used by production services and AI products. Start from a running slice, not a planning set: P2.1 produces one HTTP call, one seeded provider failure, and one regression test before any broader artifact. **Gate G1 (closes after Phase 3):** a small project that can be run, tested, debugged, and reviewed from a clean checkout, with a five-line Problem Card, a short evidence-based baseline, validated external data, an async contract with runtime evidence, and an HTTP contract and auth boundary.

**Handbook reading path (S69 [TOC]):** Ch. 36 §36.29 (responsible use of coding assistants); Ch. 37 §§37.2, 37.4–37.6, 37.13–37.15 (Python baseline, HTTP app structure, validation/error contracts, tests, project layout, production run). Keep P2.1 stub-only and preserve the existing requirement-first regression proof.

This is diagnostic and just-in-time, not beginner programming. The external-service boundaries opened here — request/response contracts, adapters, test seams — are the same boundaries the capstone hardens in Phase 4 and Phase 8; P2.1 opens the first one as a stub provider. Python implementation claims for P2.1–P2.5 are grounded in verified sources F15–F18 and `../../teaching/session-protocol.md` P§6. F2/F3/F5 support only conditional code-reading of an existing system when a named owned-system task requires it; they are not part of the default Python implementation curriculum.

- **P2.1 — Minimum reliable service: one stub-provider call, one seeded provider failure, one regression test** — **Priority:** must-have. Depends on: none. Python is fixed as the capstone language by section 2, so no language decision is re-opened here. Bootstrap the toolchain exactly as `../../teaching/session-protocol.md` P§6 specifies — one virtual environment and pinned dependencies — plus a clean Git repository. Build the smallest service that calls a local stub provider over HTTP, maps the success response to a typed object, and returns a deterministic result. Then add **one** named failure switch to the stub — for example a 503 with a provider-shaped error body — reproduce it with a deterministic fixture, write the regression test first, watch it fail against the naive implementation, correct the smallest defect, and watch it pass. Keep every other mechanism out: malformed payloads and schema validation are P2.2, timeouts and cancellation P2.3/P3.6, status classification P4.5, duplicate effects P6.5/P8.2, retry budgets P8.3, observability P9.3. **AI-dependency bridge:** this is the first provider-shaped boundary; the stub stands in for a model provider, and the seeded fault is an availability/transport fault, not a schema fault. **Proof (one primary artifact — the service repository, with checkable sub-items):** a clean checkout starts from the README run commands and the P§6 version checks are recorded in the run log; one automated test fails under the seeded fault and passes after the correction, with both runs recorded; `docs/problem-card.md` holds exactly five labelled lines — intended user, workflow, current pain or hypothesis, initial success signal, most important constraint — with every unknown marked as a hypothesis rather than a fact; and `../../workspace/evidence.md` holds the short baseline (one line per assessed dimension with the evidence that supports it, unassessed dimensions named as unassessed). No language ADR (the decision is already made), no comprehensive brief, no delivery-loop diagram, no separate CLI document, no merge-conflict exercise, and no environment-diagnosis exercise in this unit. Sources: F1, F15, F16, F17, F18; [delivery loop](../../teaching/delivery-loop.md).
- **P2.2 — Data contracts, trust boundaries, and runtime failure debugging** — Implementation unit (multi-session). **Priority:** must-have. Depends on: P2.1. JSON, schemas, serialization, missing/null/unknown fields, and enforcing validation at every entry point where data enters (HTTP requests, configuration, stored records, external-service and model-provider responses), not deep inside domain logic. Establish requirement-first test discipline: write assertions from the contract specification before writing the parsing implementation, observing tests fail (red) before they pass (green). Practice evidence-based debugging: reproduce unexpected or poisoned payload failures with a test harness, inspect traces, hypothesize, fix the validation boundary, and verify the regression test. **Conditional owned-system lab:** when verifying the existing opran codebase is relevant to the current task, compare `packages/shared/src/validation.ts` signup/login schemas with the client forms that import them (`website/src/app/login/LoginClient.tsx`, `website/src/app/signup/SignupClient.tsx`) and the shared test; determine whether the server enforces the same contract, and state what the schema does not guarantee. Skip this code-reading branch when it does not serve the selected task. **Proof:** reject malformed external payloads with actionable errors before domain logic, demonstrated with a table of valid/invalid fixtures, one of them a malformed-response mode added to the P2.1 stub and one a payload a static typechecker accepts; state which entry point each fixture covers; a bug report for an injected malformed payload with reproduction steps, cause, fix, and regression test; and test suite execution output showing requirement-first assertions. **AI-dependency bridge:** the malformed provider response is the first untrusted external payload; the schema is written from the provider contract, not from the fixture. Sources: F17, F18, S4, S21, S40, S41, S44; F2/F3/F5 apply only if the conditional TypeScript code-reading branch is selected.
- **P2.3 — Async I/O contract: concurrency, cancellation, and timeouts** — **Priority:** must-have. Depends on: P2.1–P2.2. Use existing programming knowledge over provider calls, retrieval, tools, queues, and bounded parallelism. This unit defines the async contract — which operations may run forever, which must be cancellable, how many may run at once. Runtime evidence (Python `asyncio` scheduling, resource leaks, and bounded shutdown in the capstone service) is proven by P3.6, not here; do not re-teach it. **Owned-system lab (conditional code reading):** trace opran's `website/src/components/demo/RideInputPanel.tsx` cancellation path (ADR-004) only as needed to distinguish the behavior the existing UI implements from the Python service's async contract; mark any behavior not shown in code as unverified. **Proof:** a written cancellation/timeout contract for one async call plus a bounded-parallelism implementation that honors it deterministically. Sources: F15, F18.
- **P2.4 — External-service adapters and SDK ergonomics (AI SDKs as the worked example)** — Implementation unit (multi-session). **Priority:** important. Depends on: P2.1–P2.3. Inspect the chosen Python client's request/response contract and versioning policy, pin dependencies, and isolate the provider behind a typed adapter so provider churn or SDK type gaps cannot leak into domain code. Runtime validation remains P2.2; provider behavior remains verified against the live contract or controlled fixtures, not inferred from SDK types. **Proof:** a small adapter with typed inputs, safe configuration, a pinned dependency, and tests against recorded or stub responses — the shared stub provider built in Phase 4 extends these fixtures. Sources: F15, F16, S4, S21.
- **P2.5 — Test seams for external services (provider mocks without self-deception)** — **Priority:** important. Depends on: P2.2–P2.4. Implementation unit (multi-session). Mock external-service boundaries to test contract and error paths deterministically, without pretending mocks prove real-provider or model quality; decide what the mock must reproduce (status codes, malformed payloads, latency), what it must not claim (behavior nobody has verified against the real provider), and preserve recorded fixtures for later real evaluation. The failure this addresses: a green suite that only proves the mock and the implementation share the same wrong assumption. **Proof:** unit tests for contract/error paths plus a clearly separated live smoke test run with a personal or sandbox credential, isolated from the test suite; list the assumptions the mock encodes and which later check (live test, P4.8a drift test, P14.1 evaluation) would falsify each. Sources: F18, S15.
