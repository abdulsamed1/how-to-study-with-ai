# Phase 14 — Evaluation, testing, and observability for AI systems



**Execution-order note:** This phase is intentionally learned before Phase 13, following S48's explicit 12-week sample plan. P14.1's initial requirement-derived cases are still created in M2 before any live model call; the complete evaluation mini-project follows the RAG application in P12. The same suite is extended with agent-specific cases after Phase 13 rather than postponing evaluation until after autonomy has been added.

**Goal:** Treat quality as a measured property, not a few impressive demo outputs.

**Handbook reading path (S69 [TOC]):** Ch. 21 §21.12 (LLM feature tests), Ch. 32 §32.14 (non-deterministic evaluation), Ch. 33 §33.8 (search/RAG evaluation), and Ch. 27 §§27.1–27.5, 27.9 (signals, traces, SLI/SLO). These are practical coverage/checklist sources; they do **not** close P14.3's recorded primary-source gap for statistical uncertainty, sample size, and meaningful comparison. Keep that unit's `NO-EVIDENCE` status until a suitable source is read.

- **P14.1 — Turn requirements and failures into evaluation cases** — **Priority:** must-have. Depends on: P2.1, P7.2. Coupled with: P11.6 (the first case set is built from the P10.1 workflow and the P7.2 test discipline; P11.6's architecture decision can add or invalidate cases, so the set is revisited there, but P11.6 is not a prerequisite for the first set). Build representative, edge, and adversarial cases from real workflows and documented failure modes. The first set can be completed before the first model call (P11.2); model-specific cases are added after P11.2–P11.3, and the formal graders in P14.2 wait for P11.3. **Proof:** versioned evaluation set with expected outcomes and provenance; the first cases are written by the learner before any agent expands the set. Sources: S15 (2026-01-09 refresh: start with 20–50 tasks from real failures, isolate trials, read transcripts, eval-driven development); S22 (deprecated — see the S22 note in §7).
- **P14.2 — Graders: code-based, model-based, and human review** — **Priority:** important. Depends on: P14.1, P11.3. Choose a grader that matches the property; analyze false positives/negatives and judge reliability. Grader-design vocabulary and choices (S59): direct (pointwise) scoring suits objective properties (faithfulness, policy violations) while pairwise comparison is more stable for subjective ones but does not fit faithful-to-source tasks; judge calibration checks agreement with human labels using conservative agreement statistics named at vocabulary level (percent agreement, Cohen's kappa in its fair/moderate ranges); and the documented judge biases — higher-score and verbosity preference, position/order in pairwise presentation, sensitivity to paraphrased prompts — are controlled by randomized order, neutral rubrics, and sufficient sample size rather than trusted away. **Proof:** compare grader decisions against a human-reviewed sample. Sources: S15, S59; S22 (deprecated — see the S22 note in §7). Grader pattern: single-call 0.0–1.0 LLM judge against a rubric (factual accuracy, citation accuracy, completeness, source quality, tool efficiency) per S8.
- **P14.3 — Quality dimensions and statistical uncertainty** — Implementation unit (multi-session). **Priority:** important. Depends on: P14.1–P14.2, P9.4. Sample size, run-to-run variation, confidence, slices, and meaningful before/after comparison. **Proof:** evaluation report that states limits and avoids overclaiming. State the decision rule (what change would count as real) before looking at results. **Method (interim, mentor synthesis — not a statistics text; rule 9 caps math here):** fixed prompts and seeds, at least three repeats on small sets, report n plus observed range, split results by failure slice, compare before/after on identical sets only, and pre-register a block threshold calibrated from baseline repeat noise. Sources: none yet — NO-EVIDENCE (interim mentor synthesis); `../../workspace/resources.md` still records a primary statistics tutorial as missing.
- **P14.4 — Regression gates and change management** — **Priority:** must-have. Depends on: P11.5, P12.6, P14.1–P14.3. Re-run evaluations when prompts, models, retrieval, tools, or policies change (the versioned configuration from P11.5 defines what counts as a change), and block a release that regresses the evaluation set. The failure this addresses: a quiet prompt or model swap reaching users because nothing re-ran. **Proof:** CI or documented release gate that blocks a known regression, plus one executed rerun after a versioned prompt or model change with the before/after results recorded. Sources: S15.
- **P14.5 — Trace a complete AI request** — **Priority:** important. Depends on: P9.3, P11.2–P11.4, P12.4–P12.5. Coupled with: P13.3 (extend the same trace contract to agent steps after the bounded loop exists; this is not a prerequisite). Trace the Docs Q&A path end to end — question, retrieval candidates/reranking, model request, citation or abstention, errors, and token/cost/latency fields where actually available — with sensitive data redacted. A documented platform option (S60): Langfuse's trace→session→evaluator→dataset flow spans online scoring of live traces, offline dataset experiments, judge calibration, and a CI regression gate — a concrete reference shape for what a trace platform should support; adopting such a platform is an integration decision against the existing stack, not a prerequisite of this unit. **Proof:** diagnose a seeded Docs Q&A failure from a recorded trace and name what cannot be inferred from that trace. After Phase 13, add agent/tool spans and extend the evaluation cases without making agent execution a prerequisite for this first proof. Sources: S9, F9, S21, S60.
- **P14.6 — Failure analysis and operational learning loop** — **Priority:** important. Depends on: P9.5, P14.1–P14.5. Classify failures, add a regression case, make one change, and measure it. **Proof:** one complete loop from observed failure to verified improvement. Sources: S9, S15.
- **P14.7 — Production-side evaluation loop** — **Priority:** important. Depends on: P9.3–P9.5, P14.4. Boundary: the regression gate (P14.4) runs in CI; this unit connects Phase 9 telemetry to the P14 metrics so quality degradation is *seen in production*, not only in eval runs — sampled trajectory review, drift signals on inputs/outputs/latency/cost, and one alert wired from a P9.4 SLI to a simple chart on the existing observability stack (no pre-existing eval dashboard required). **Proof:** a production evaluation plan that maps each monitored signal to the metric or failure mode it detects, plus one wired alert and one sampled trajectory review from the telemetry. Sources: S15, S9.
