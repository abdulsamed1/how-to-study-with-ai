# Phase 9 — Production resilience, infrastructure, and scale

**Goal:** Diagnose and operate production behavior from evidence. Design service infrastructure and fault boundaries that keep a local failure from becoming a system-wide incident.

**Handbook reading path (S69 [TOC]):** Ch. 24–27 and 36 as mapped below. Provider-specific cloud, container, and orchestration behavior must be checked against current official documentation when selected.

- **P9.1 — Runtime configuration, containers, and environments** — **Priority:** important. Depends on: P3.4, P3.7, P5.6, P7.2. Build a reproducible container and separate local/test/production configuration. **Proof:** clean startup following written instructions. Sources: F7, S26.
- **P9.2 — CI/CD and safe release workflow** — **Priority:** must-have. Depends on: P2.1, P5.5, P7.2, P9.1. Automated checks, build artifacts, deployment steps, migrations, rollout, and rollback limits. **Proof:** CI builds/tests the service and a rollback rehearsal records what could and could not be reversed. Review agent-written pipeline changes for secrets, permissions, and mutable references. Sources: F7, S25, S34, S36.
- **P9.3 — Logs, metrics, traces, and correlation** — **Priority:** must-have. Depends on: P4.7b, P8.4–P8.5, P9.1. Understand what each signal answers and correlate one request across components. **Proof:** trace a request using a correlation ID; locate one seeded fault from logs, trace, and one runtime measurement before reading the code. Sources: F9, S25, S39.
- **P9.4 — SLIs, SLOs, error budgets, and alerts** — **Priority:** must-have. Depends on: P9.3, P2.1. Define user-visible reliability and alert on actionable symptoms. **Proof:** compute one SLI from recorded stub-provider fault runs, propose an SLO with rationale, and show an alert fires on an injected failure but stays quiet on noise. Sources: S25, F10, S19 ch. 2.
- **P9.5 — Incident response and postmortems** — **Priority:** important. Depends on: P9.3–P9.4, P8.3. Stabilize, gather evidence, communicate, restore service, and learn without prematurely declaring root cause. **Proof:** incident timeline, mitigation, causal mechanism, prevention items, and stakeholder update separating impact, facts, unknowns, and next update. Sources: S9, S10, S25, S35.
- **P9.6 — Performance diagnosis and capacity reasoning** — **Priority:** important. Depends on: P5.4, P8.3, P9.3–P9.5. Latency percentiles, throughput, saturation, queueing, resource pools, database bottlenecks, and workload shape. The performance journey owns detailed profiling and load-testing methods; this unit owns diagnosis in the FDE capstone. **Proof:** diagnose a controlled load test before selecting a fix. Sources: ../performance/study-overview.md, S19, S25.
- **P9.7 — Graceful degradation, service-level recovery, and runbooks** — **Priority:** must-have. Depends on: P5.7, P8.0c, P8.0e, P8.3–P8.7, P9.2–P9.6. Choose degradation and recovery controls against named failure and business targets. Define RTO/RPO before drills. Evaluate circuit breakers, bulkheads, caching, and human/deterministic fallback as candidate controls, not automatic checkboxes. **Proof:** executed fault matrix covering provider outage, duplicate-delivery storm, expired credential, worker crash, and bad configuration, plus a runbook another engineer can follow. Sources: S25, F10, S27 ch. 24–28 [TOC], S35.
- **P9.8 — Service discovery, load balancing, and service communication infrastructure** — **Priority:** important. Depends on: P4.1, P7.1, P8.0a, P9.1. Understand DNS-based and registry-based service discovery, registration/health, L4 versus L7 load balancing, reverse proxies, API gateways, readiness, and sidecar/service-mesh roles. Compare gateway and mesh responsibilities; do not make Kubernetes or a service mesh a default prerequisite. **Proof:** map a request across service discovery, proxy/load-balancer, and service instances; analyze what happens when an instance is unhealthy or a registry entry is stale; justify the simplest adequate infrastructure. Sources: S27 ch. 4 (selected sections read); S26 ch. 5 (selected sections read); S20 ch. 14 [TOC]; S29 ch. 6 (selected sections read).
- **P9.9 — Caching, replicas, and read scaling** — **Priority:** important. Depends on: P5.4, P8.0c, P9.6. Compare local/distributed caches, cache-aside, TTL, invalidation, stale reads, hot keys, stampedes, cache failure/collapse, reverse proxies/CDNs, and read replicas. Separate measured diagnosis (P9.6) from mechanism selection (P10.5). **Proof:** test hit/miss/stale/unavailable-cache paths, show origin load remains bounded during a cache failure, and document freshness/invalidation behavior. Sources: S28 ch. 6 (read); S20 ch. 16 [TOC]; S19 ch. 6 (read).
- **P9.10 — Redundancy, failure domains, and fault isolation** — **Priority:** important. Depends on: P8.0c, P8.0e, P9.3–P9.7, P9.8. Understand independent failure domains, correlated failure, blast radius, redundancy, failover, cells/cellular architecture, tenant isolation, shuffle sharding, and the limits of bulkheads. **Proof:** draw a failure-domain map and run a controlled fault test showing one component/tenant failure remains within a declared blast radius; explain the cost of the isolation boundary. Sources: S27 ch. 23 and 26 (selected sections read); S26 ch. 12 (selected sections read); S29 ch. 16 (read).
- **P9.11 — Chaos engineering and resilience validation** — **Priority:** useful. Depends on: P7.2, P9.3–P9.7, P9.10. Form a falsifiable resilience hypothesis, define steady-state signal, blast radius, abort conditions, controlled fault, rollback, and post-experiment review. Distinguish local fault injection and game days from production chaos experiments; production experiments require explicit authorization and safeguards. **Proof:** safe, bounded fault experiment report with hypothesis, guardrails, observations, deviations, and follow-up actions. Sources: S25; S26 ch. 12 (selected sections read).
