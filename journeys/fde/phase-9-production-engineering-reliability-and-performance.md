# Phase 9 — Production engineering, reliability, and performance



**Goal:** Diagnose production behavior from evidence and run changes safely. Agent-authored pipeline, migration, and configuration changes get the same review and rehearsal as application code.

**Handbook reading path (S69 [TOC]):** Ch. 24 §§24.1–24.4, 24.7–24.12, 24.14 (containers, reproducibility, image security, configuration); Ch. 25 §§25.1–25.3, 25.5–25.10, 25.13–25.17 (pipeline stages, artifacts, migrations, rollout/rollback, gates, secrets, release checks); Ch. 27 §§27.1–27.14 (logs/metrics/traces, alerts, SLI/SLO, load tests, incident response, recovery drills); Ch. 36 §§36.9, 36.18–36.20, 36.26 (processes, env vars, log search, SSH, database utilities). Ch. 26 is a deployment-target-specific path: use its GCP sections only if GCP is selected; do not treat its provider-specific commands as general cloud rules.

- **P9.1 — Runtime configuration, containers, and environments** — **Priority:** important. Depends on: P3.4, P3.7, P5.6, P7.2. Build a reproducible container and separate local/test/production configuration. **Proof:** clean startup following written instructions. Sources: F7, S26.
- **P9.2 — CI/CD and safe release workflow** — **Priority:** must-have. Depends on: P2.1, P5.5, P7.2, P9.1. Automated checks, build artifacts, deployment steps, migrations, and rollback limits. **Owned-system lab:** compare opran's CI and deployment workflows (`.github/workflows/ci.yml`, `deploy.yml`, `rollback.yml`) with this unit's checklist; name one control that is present, one that is missing or unverified, and what `rollback.yml` actually does. **Proof:** CI runs tests and builds the service, plus a rollback rehearsal: deploy version N+1 with a migration, roll back to N, and state what could not be rolled back; one conflicted merge on a rehearsal branch is resolved, the resolution explained, and the tests re-run after resolution (the merge-conflict exercise relocated here from P2.1); review any agent-written pipeline or workflow change for secrets, permissions, and mutable references (the CI trust-boundary lesson in S34). Sources: F7, S25, S27 ch. 29–30 [TOC], S34, S36.
- **P9.3 — Logs, metrics, traces, and correlation** — **Priority:** must-have. Depends on: P4.7b, P8.4–P8.5, P9.1. Understand what each signal answers and correlate one request across components. **Proof:** trace a request using a correlation ID and explain its timeline, then locate one seeded fault from the logs, the trace, and one runtime measurement before reading the code. **AI-dependency bridge:** trace the P2.1 provider call (now through the P4.7b harness) through the service with one correlation ID, and show the provider request id, the error path, and the business step in one timeline. Sources: F9, S25, S39 (§3.2.1, REC-API-18).
- **P9.4 — SLIs, SLOs, error budgets, and alerts** — **Priority:** must-have. Depends on: P9.3, P2.1. Define user-visible reliability and alert on actionable symptoms rather than every noisy signal. **Owned-system lab:** compute Eagles' acknowledgement-SLA SLI from test or recorded assignment data behind `eagles-wrms-app/src/logic-functions/monitor-sla.logic-function.ts` (30-minute business-time rule, one-minute cron), and label the PRD target separately from the measured result. **Proof:** compute one SLI from recorded stub-provider fault runs, propose an SLO with rationale (justify any threshold in an ADR rather than inventing one), and show the alert condition fires on an injected failure and stays quiet on noise. Sources: S25, F10; S29 ch. 2 (read: API SLOs — latency, reliability, throughput; percentiles; reliability measured at the response-code level), ch. 16 (read: absent errors and client-versus-expected error buckets); S27 ch. 31 [TOC], S19 ch. 2.
- **P9.5 — Incident response and postmortems** — **Priority:** important. Depends on: P9.3–P9.4, P8.3. Stabilize, gather evidence, communicate, restore service, and learn without prematurely declaring root cause. **Proof:** incident timeline, mitigation, causal mechanism, and prevention items, plus a stakeholder update that separates impact, known facts, unknowns, and the next update time. Sources: S9, S10, S25, S35 (case), S36 (stated plan, not a measured outcome).
- **P9.6 — Performance diagnosis and capacity reasoning** — **Priority:** important. Depends on: P5.4, P8.3, P9.3–P9.5. Latency percentiles, throughput, saturation, queueing, resource pools, database bottlenecks, and workload shape. **Proof:** diagnose a controlled load test before selecting a fix. **AI-dependency bridge:** use the P4.7b harness's latency mode as the slow provider, record p95 latency and the resource that saturates, and state which explanation the measurement rules out before choosing a fix. Source: `../performance/study-overview.md`, S19, S25.
- **P9.7 — Graceful degradation, service-level recovery, and runbooks** — **Priority:** must-have. Depends on: P5.7, P8.3–P8.7, P9.2–P9.6. Scope boundary: what to degrade under dependency pressure and how the service recovers as a system; the data-level backup/restore proof stays in P5.7 — this unit reuses that restore inside RTO/RPO-style drills; no re-teaching. The lesson defines RTO and RPO before the drills use them. Evaluate circuit breakers, bulkheads, caching, and human/deterministic fallback as candidate controls against the named failure and recovery target; none is an automatic checkbox. **Proof:** an executed fault matrix against the stub provider (provider outage, duplicate-delivery storm, expired or revoked credential, worker crash, bad configuration file) using the [failure-matrix template](journey-overview.md#3-lesson-design-and-completion-criteria) with recovery columns filled, plus a runbook a second person can follow without undocumented oral context, with time-to-restore and deviations recorded. Sources: S25, F10, S27 ch. 24–28 [TOC], S29 ch. 16 (read: common failure patterns), S35, S36; S69 ch. 20 §§20.5–20.6 [TOC].
